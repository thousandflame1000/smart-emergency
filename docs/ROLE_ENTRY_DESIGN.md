# 三角色 LINE 入口設計

## 問題判讀

舊版將 11 至 14 個功能平鋪在每張 Rich Menu，居民、志工與管理員都會看到不屬於當下任務的選項。這會造成三種失敗：

- 居民在壓力下還得先判斷需求類型，可能錯過「需要幫忙」這個緊急入口。
- 志工把接單、任務、物資、自己的居民服務混在同一層，難以判斷下一個可完成的動作。
- 決策者在求救、派遣、核准與一般志工操作之間切換，重要資訊被操作雜訊淹沒。

把所有資訊都壓在 Rich Menu 也不是完整告知。它只會讓資訊同時可見，不能讓資訊依風險、權限與任務順序被理解。

## 角色入口

| 角色 | 主選單六格 | 中心卡片提供的完整資訊 |
| --- | --- | --- |
| 居民 | 緊急求助、申請需求、查看進度、回報平安、分享位置、居民中心 | 需求紀錄、家屬綁定、志工申請、操作說明；照護聯絡人另見長輩狀況 |
| 志工 | 接單、我的任務、登記物資、志工中心、分享位置、需要幫忙 | 我的物資、撤回物資、位置與操作說明 |
| 決策者 | 決策中心、緊急求救、待派需求、待審志工、開啟後台、操作說明 | 即時風險量、待派與建議數、任務、申請、每日長者狀態與完整後台 |

家屬保留為照護關係與權限，不是第四個全域角色。這讓一位同時是家屬與居民的人不必在兩張互相重疊的選單間切換；系統在他開啟「居民中心」時才顯示「家庭照護」與「長輩狀況」。

## 資料與權限原則

- 中心卡片的按鈕只送出既有 LINE 指令，仍由原本的 handle_text、角色檢查、派遣服務與資料庫交易處理。
- 家屬綁定、需求、物資、任務與派遣 ID 沒有重新編號或複製；只改變入口呈現。
- 志工物資仍以擁有者與資源類型更新，派遣仍走既有保留與稽核路徑；卡片不直接修改任何庫存或派遣資料。
- 決策中心只顯示彙整資料；實際派遣、求救結案與申請核准仍在既有、具權限檢查的操作中完成。

## 受控更新

Rich Menu 重建是刪除既有遠端選單、建立新選單、上傳圖片並重新連結使用者的批次寫入。因正式網域上傳受限，日常 LINE 指令與 API 預設都不允許執行。

在本機先產生並檢查三張 PNG。待程式與圖片集中為一次最小部署後，才由維運人員暫時設定 RICH_MENU_REBUILD_ENABLED=true，執行一次重建並立即關閉。不得在測試、聊天或重試迴圈中反覆呼叫。
